## 소개

**한 서비스의 앱, 웹, 배포를 혼자 감당해 봤습니다.** 여행 코스 추천 서비스 '동행'에서 Flutter 앱과 Next.js 웹을 1인 전담으로 개발해 Android 내부 테스트 배포까지 진행했습니다. MEOVA에서는 Django 백엔드와 Vue 프론트엔드를 함께 구현하고 서버 배포까지 담당했습니다. 프론트와 백엔드 어느 쪽에 서든, 반대편이 무엇을 필요로 하는지 아는 상태로 일합니다.

**계약은 합의하는 것이 아니라 실측하는 것이라고 믿습니다.** 동행에서 백엔드가 요청 스키마를 바꿨을 때 앱이 따라가지 못해 회원가입이 통째로 막힌 적이 있습니다. 문서와 합의가 아니라 배포된 코드에서 계약을 확인하는 습관을 이때 만들었고, 요청 스키마를 계약 테스트로 고정해 이후의 변경은 테스트가 먼저 잡아내도록 했습니다.

**AI가 틀렸을 때 시스템이 어떻게 되는지를 먼저 설계합니다.** MEOVA에서 ChatGPT가 DB에 없는 영화를 지어내 추천하는 문제를 겪었습니다. 프롬프트로 "지어내지 마"라고 설득하는 대신 영화를 ID로 반환하게 만들어, 지어낸 결과가 조회 시점에 자연히 걸러지는 구조로 풀었습니다. LLM을 서비스에 넣을 때 중요한 것은 프롬프트의 정교함보다 오답을 흡수하는 구조라고 생각합니다.

# 프로젝트

## 1. 동행 (Donhaeng) — 취향 기반 AI 여행 코스 추천 서비스

**5060 액티브 시니어를 위한 여행 플래닝 서비스. Flutter 앱과 Next.js 웹을 1인 전담했습니다.**

| | |
|---|---|
| 기간 | 2026.07 ~ 진행 중 |
| 플랫폼 | Android · iOS (Flutter) / 웹 (Next.js 15) |
| 팀 | 프론트엔드 1(본인), 백엔드 1 외 |
| 역할 | **앱 · 웹 프론트엔드 전담, 배포 담당** |
| 배포 | Android 내부 테스트 (v1.0.0+1), Firebase Hosting |
| 기술 | Flutter, Riverpod / Next.js 15, TypeScript, TailwindCSS / Firebase Auth, Kakao Map SDK, App Links |

### 문제 정의

여행 계획은 정보 검색, 동선 구성, 시간 배분이 겹치는 부담스러운 작업인데, 기존 앱은 정보를 나열할 뿐 코스를 대신 짜 주지 않습니다. 앱을 설치하지 않은 사람에게도 코스가 전달돼야 서비스가 퍼질 수 있어, **앱(생성·관리)과 웹(공유·유입)을 하나의 흐름**으로 설계했습니다.

### 담당 업무

**앱** — 온보딩부터 설정까지 전 화면, 소셜 로그인 3종, 코스 생성(SSE 스트리밍), 지도 동선, AdMob 리워드 광고, 공유·저장 딥링크

**웹** — 코스 공유 페이지(SSR + 동적 OG), 약관 4종·계정 삭제 안내 페이지, Firebase Hosting 배포 구성

**구조** — 앱은 Clean Architecture(data / domain / presentation), 웹은 UI → services → repository → types 계층 분리. 컴포넌트는 `getShareService()`만 호출하고 백엔드를 직접 알지 못하며, mock과 실제 백엔드를 설정 한 줄로 교체할 수 있습니다.

### 기술적 도전

#### ① 카카오톡 공유 미리보기가 뜨지 않는 문제

**문제** · 코스 공유 링크를 카카오톡에 보내면 미리보기(OG)가 나오지 않았습니다. 카카오톡 크롤러는 JS를 실행하지 않기 때문에, OG 태그가 **초기 HTML에** 들어 있어야 합니다.

**해결** · 코스 페이지를 요청 시점 SSR로 렌더하도록 Firebase Hosting의 웹 프레임워크 인지 배포를 사용했습니다. 정적 자산은 CDN으로, 코스 SSR은 Cloud Run으로 자동 분리됩니다. 조회 이벤트는 클라이언트가 same-origin 라우트로 보내고 서버가 백엔드로 프록시해, CORS 문제와 백엔드 주소 노출을 함께 막았습니다.

**결과** · 카카오톡·SNS에서 코스 제목과 이미지가 미리보기로 표시되고, 백엔드 주소는 브라우저에 노출되지 않습니다.

#### ② 공유 링크를 다시 누를 때마다 여행이 중복 생성되는 문제

**문제** · 공유 딥링크로 코스를 저장할 때 서버는 호출마다 새 여행을 만들었습니다. 사용자가 링크를 두 번 누르면 같은 여행이 두 개 쌓입니다.

**해결** · 저장 요청에 멱등키(`X-Idempotency-Key: save-shared-{token}`)를 실었습니다. 서버가 키를 사용자 단위로 구분하므로, 같은 사용자가 몇 번을 눌러도 같은 여행 ID가 돌아옵니다. 응답 파싱도 실제 스키마에 맞게 바로잡고, 존재하지 않는 필드에 대한 의존을 제거했습니다.

**결과** · 딥링크를 반복 탭해도 여행이 하나만 만들어집니다.

#### ③ 백엔드 스키마 변경으로 회원가입이 전면 실패

**문제** · 회원가입이 422 에러로 실패하고 있었습니다. 백엔드가 요청 스키마에서 필드를 삭제·추가했는데 앱이 반영하지 못했고, 서버가 정의되지 않은 필드를 거부하도록 설정돼 있어 가입 자체가 막혔습니다.

**해결** · 배포된 백엔드의 실제 계약을 코드로 확인해 필드를 맞추고, 요청 body의 키와 필수 필드를 **계약 테스트로 고정**했습니다. 이후 코스 평가 API가 배열 필드로 바뀌었을 때도 테스트가 먼저 잡아냈습니다. 자유 코멘트에는 300자 제한을 클라이언트에 걸어 서버 422가 아예 발생하지 않도록 했습니다.

**배운 것** · 문서와 합의는 배포된 코드와 다를 수 있습니다. 프론트가 백엔드 계약을 실측하고 테스트로 고정해 두면, 스키마 변경은 장애가 아니라 테스트 실패로 먼저 나타납니다.

#### ④ 지도 API 키가 클라이언트에 노출되는 문제

**문제** · 길찾기(directions) 호출을 앱에서 직접 하면 REST 키가 클라이언트에 실립니다.

**해결** · 호출을 백엔드 프록시(POST /v1/directions)로 옮기고 클라이언트에서 키를 제거했습니다. 실패 시 직선 경로 폴백은 유지했습니다. 로그인 실패 시 서버 에러 원문이 사용자에게 노출되던 것도 고정 안내 문구로 교체하고 원문은 디버그 로그로만 남겼습니다.

### 성과

- **Android 내부 테스트 배포 완료** (릴리스 AAB 서명 빌드 검증) + 웹 Firebase Hosting 배포 구성
- 앱·웹 프론트엔드 **1인 전담**으로 Phase 1 전체 기능 구현
- **테스트 42건 통과**, `flutter analyze` error·warning 0건 유지, 계약 테스트 도입
- 실기기(Galaxy Note9) 스모크 QA 수행 및 리포트 문서화

> 상세: cadetbluee.github.io/project/donhaeng

## 2. MEOVA — 태그 기반 SNS 영화 추천 플랫폼

**상황과 관계에 맞는 영화를 태그로 찾는 웹 서비스. 2인 팀에서 백엔드와 프론트엔드, 배포를 함께 담당했습니다.**

| | |
|---|---|
| 기간 | 2024.05 (3주) |
| 플랫폼 | Web (반응형) |
| 팀 | 2인 (풀스택 2) |
| 역할 | **BackEnd, FrontEnd, 서버 배포**, UI·UX 디자인, 기획 |
| 성과 | **웹 프로젝트 최우수상 (1위)** |
| 기술 | Vue, Django, MySQL, TMDB API, OpenAI API |

### 문제 정의

함께 볼 영화를 고를 때 "뭐 보지?"에 시간을 다 쓰고, 추천받은 영화에 노골적이거나 잔인한 장면이 있어 불편했던 경험에서 출발했습니다. 평점 하나로는 전달되지 않는 정보가 있다고 판단해, 관람 상황에 맞는 **태그 검색**과 선정성·폭력성 요소를 미리 알려 주는 **태그 코멘트**를 핵심 기능으로 잡았습니다.

### 담당 업무

- 로그인 서버 구현, 영화·리뷰 기능의 백엔드와 프론트엔드
- **ChatGPT 데일리 추천** — 프롬프트 설계와 응답 파싱
- TMDB 영화 데이터 적재(fixture 구성), Django view 구현
- **서버 배포**, 디버깅과 오류 수정, 발표 자료 작성

### 기술적 도전 — AI가 존재하지 않는 영화를 추천하는 문제

**문제** · "독창적인 컨셉으로 영화 3개를 추천해줘"라고 요청하면, ChatGPT가 **DB에 없는 영화를 그럴듯하게 지어내서** 반환했습니다. 추천은 자연스러운데 클릭하면 상세 페이지가 없는 상황이 됩니다. 매일 자동으로 도는 기능이라 사람이 검수할 수도 없었습니다.

**해결** · DB의 전체 영화 목록을 `제목(ID)` 형태로 프롬프트에 넣고, 시스템 메시지로 응답 형식을 고정해 **영화를 제목이 아닌 ID로 반환**하게 했습니다. ID로 받으면 DB 조회 시점에 존재하지 않는 영화가 자연히 걸러집니다.

**배운 것** · "지어내지 마"라고 부탁하는 대신, **지어내도 시스템이 무사한 구조**를 만드는 것. 2024년 초에 LLM을 서비스에 붙이며 얻은 이 원칙은 지금도 그대로 유효합니다.

### 성과

- 🏆 **SSAFY 웹 프로젝트 최우수상 (1위)**
- 2인 팀으로 3주 만에 태그 검색, AI 추천, 커뮤니티, 반응형, 다크 모드를 갖춘 풀스택 웹 완성
- 백엔드부터 배포까지 전 구간 경험 — 이후 프론트엔드 중심 프로젝트에서 백엔드 계약을 읽는 기반이 됨

> 상세: cadetbluee.github.io/project/meova

## 3. PushOfLife — 응급 구조 지원 · CPR 실시간 피드백

**갤럭시 워치가 낙상을 감지해 자동으로 신고하고, 구조자의 워치에서 CPR 가이드를 자동 실행합니다.**

| | |
|---|---|
| 기간 | 2024.10 ~ 2024.11 (6주) |
| 플랫폼 | Android App · Wear OS |
| 팀 | 6인 (FE/Mobile 2, WearOS 2, BE 2) |
| 역할 | FE/Mobile, UI·UX 디자인, 기획 — **커밋 150개, 팀 내 최다 기여** |
| 성과 | **자율 프로젝트 전국대회 일등상** |
| 기술 | Kotlin, Jetpack Compose, Wear OS SDK, BLE, FCM, Twilio |

### 문제 정의

병원 밖 심정지는 초기 몇 분이 생존율을 결정하는데, 그 몇 분이 "신고해야 하나, 내가 해도 되나"를 고민하는 데 쓰입니다. 워치의 기본 센서만으로 상황을 자동 감지해 신고하고, 구조자에게는 압박 깊이·빈도·각도를 실시간 피드백하는 서비스를 기획했습니다.

### 기술적 도전

**① 실시간 센서 데이터로 인한 프레임 드랍** · 초당 수십 회 들어오는 가속도 데이터가 매번 Compose 재구성을 일으켰습니다. `remember` 캐싱으로 불필요한 재구성을 차단하고, 그래프가 보관하는 데이터 개수를 고정해 축 흔들림을 없앴습니다. 센서 원시값은 저주파 필터와 칼만 필터로 노이즈를 제거했습니다. **결과: 프레임 드랍 약 50% 감소.**

**② 오작동이 곧 피해가 되는 기능** · 자동 신고는 오탐이면 구급차가 헛출동합니다. 감지 즉시 신고하지 않고 **움직임이 있으면 종료, 없을 때만 신고**하는 2단계 구조로 설계하고, 신호 신뢰도에 따라 대기 시간을 워치 3초·모바일 30초로 다르게 두었습니다.

**③ BLE 3단계 릴레이** · 환자 워치 → 모바일 → 구조자 워치로 이어지는 통신에서, 리시버 해제 누락으로 이전 연결이 남는 문제를 잡는 데 시간을 많이 썼습니다. 연결형 통신에서는 연결하는 코드만큼 정리하는 코드가 중요하다는 것을 배웠습니다.

### 성과

- **프레임 드랍 약 50% 감소**, 모바일·워치 BLE 양방향 통신 구현
- 🏆 SSAFY 자율 프로젝트 **전국대회 일등상**

> 상세: cadetbluee.github.io/project/pushoflife
