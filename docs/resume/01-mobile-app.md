## 소개

**서비스를 기획부터 배포까지 완주한 경험이 있습니다.** 여행 코스 추천 앱 '동행'의 Flutter 앱과 Next.js 웹 프론트엔드를 혼자 맡아 Android 내부 테스트 배포까지 진행했습니다. 기능 구현만이 아니라 스토어 배포, 실기기 QA, 백엔드 계약 검증까지 프론트엔드가 책임지는 범위 전체를 경험했습니다.

**동작하는 화면과 정직한 화면을 구분합니다.** 동행에는 AI 코스 생성이 실패하면 미리 만들어 둔 더미 일정을 보여주는 폴백이 있었습니다. 화면은 문제없어 보였지만, 사용자는 AI가 짜 준 코스라 믿고 그 일정대로 여행을 떠나게 됩니다. 폴백을 걷어내고 빈 상태·에러 화면으로 교체했습니다. 실패를 감추기보다 다시 시도할 기회를 주는 편이 낫다고 판단했기 때문입니다.

**같은 문제를 두 번 만나면 다르게 풉니다.** 2024년 AllEat에서는 '방금 등록한 기록이 홈에 보이지 않는' 문제를 화면마다 갱신 코드를 넣어 해결했습니다. 2026년 동행에서 같은 증상을 다시 만났을 때는 이것이 상태 소유권의 문제임을 알아차리고, `RouteObserver`로 갱신이 필요한 시점을 한곳에서 감지하도록 구조를 바꿨습니다.

# 프로젝트

## 1. 동행 (Donhaeng) — 취향 기반 AI 여행 코스 추천 앱

**5060 액티브 시니어를 위한 여행 플래닝 앱. 버튼 한 번이면 AI가 일차별 코스를 만들어 줍니다.**

|        |                                                                        |
| ------ | ---------------------------------------------------------------------- |
| 기간   | 2026.07 ~ 진행 중                                                      |
| 플랫폼 | Android · iOS (Flutter) / 웹 (Next.js)                                 |
| 팀     | 프론트엔드 1(본인), 백엔드 1 외                                        |
| 역할   | **Flutter 앱 · Next.js 웹 프론트엔드 전담**                            |
| 배포   | Android 내부 테스트 (v1.0.0+1)                                         |
| 기술   | Flutter, Riverpod, dio, Firebase Auth, Kakao Map SDK, AdMob, App Links |

### 문제 정의

여행 계획은 정보 검색, 동선 구성, 시간 배분이 겹치는 부담스러운 작업인데, 기존 여행 앱은 정보를 나열할 뿐 코스를 대신 짜 주지 않습니다. 특히 5060 사용자는 여행 수요는 크지만 작은 글씨와 복잡한 다단계 플로우 앞에서 이탈합니다. **접근성이 곧 사용 여부를 결정하는 사용자층**이라고 판단해, 코스 자동 생성과 시니어 기준 UI를 함께 설계했습니다.

### 담당 업무

- 취향 온보딩(카드 스와이프·튜토리얼), 홈, AI 코스 생성, 지도 동선, 코스 평가, 내 여행, 설정 등 전 화면 구현
- 소셜 로그인 3종(Google, Kakao·Naver WebView OAuth)과 약관 동의 플로우
- App Links / Universal Links 기반 코스 공유·저장 딥링크
- AdMob 리워드 광고와 서버 권위 쿼터 연동
- Clean Architecture(data / domain / presentation) 구조 설계, 디자인 토큰 단일 출처 운영

### 기술적 도전

#### ① 튜토리얼 코치마크가 안내 대상 버튼을 가리는 문제

**문제** · 온보딩 튜토리얼의 딤 레이어가 화면 전체를 덮어, "이 버튼을 누르세요"라고 안내하는 좋아요·건너뛰기 버튼까지 어두워졌습니다. 디지털에 익숙하지 않은 사용자일수록 이런 지점에서 멈춥니다.

**해결** · 대상 버튼에 `GlobalKey`를 붙여 첫 프레임 이후 화면 좌표를 측정하고, 딤을 `ColoredBox`에서 `CustomPaint`로 교체해 `Path.combine(difference)`로 해당 영역만 도려냈습니다. 좌표 측정에 실패하면 기존 전체 딤으로 폴백해 화면이 깨지지 않게 했고, 터치는 그대로 딤이 흡수해 튜토리얼 진행 순서는 유지했습니다.

**결과** · 안내 대상만 밝게 남아 시선이 정확히 유도되고, 측정에 실패해도 화면이 깨지지 않습니다.

#### ② 방금 만든 여행이 홈 목록에 보이지 않는 문제

**문제** · 코스를 만들고 홈으로 돌아와도 목록에 반영되지 않았습니다.

**원인** · `myTripsProvider`는 캐시여서 무효화 없이는 갱신되지 않는데, 앱 복귀(`resumed`) 시점에만 무효화하고 있어 **지도에서 뒤로가기로 홈에 돌아오는 경로**가 빠져 있었습니다. 코스 생성 흐름이 `pushReplacement`로 이어져 push future를 기다리는 방식으로는 복귀 시점을 잡을 수 없다는 제약도 있었습니다.

**해결** · `RouteObserver`를 등록하고 `HomeScreen`을 `RouteAware`로 만들어 `didPopNext`에서 무효화했습니다. 대상을 `PageRoute`로 한정해 광고 시트 같은 모달이 닫힐 때는 재조회하지 않도록 했습니다.

**결과** · 복귀 경로와 무관하게 최신 코스가 반영됩니다. 화면마다 갱신 코드를 심는 대신 **갱신이 필요한 순간을 한곳에서 감지**하는 구조가 됐습니다.

#### ③ 백엔드 스키마 변경으로 회원가입이 전면 실패

**문제** · 회원가입이 422 에러로 실패하고 있었습니다. 백엔드가 요청 스키마에서 `locationAgreed`를 삭제하고 `ageVerifiedOver14`를 필수로 추가했는데 앱이 반영하지 못한 상태였고, 서버의 `extra="forbid"` 설정 때문에 조용히 무시되는 대신 가입 자체가 막혔습니다.

**해결** · 배포된 백엔드의 실제 계약을 코드로 확인해 필드를 맞추고, 동의 시트를 법무 정본 순서로 재배치했습니다. "개인정보 처리방침 동의"라는 잘못된 표기도 "개인정보 수집·이용 동의"로 바로잡았습니다. 처리방침은 게시 문서이지 동의 체크 대상이 아니기 때문입니다.

**재발 방지** · 요청 body의 키와 필수 필드를 **계약 테스트로 고정**했습니다. 이후 코스 평가 API가 바뀌었을 때도 테스트가 먼저 잡아냈습니다. 자유 코멘트에는 300자 제한을 클라이언트에 걸어 서버 422가 아예 발생하지 않도록 했습니다.

**배운 것** · 문서와 합의는 배포된 코드와 다를 수 있습니다. 계약은 합의하는 것이 아니라 실측하는 것입니다.

### 시니어 접근성

수치 기준을 정해 **디자인 토큰에 고정**하고, 개별 화면에서 매직넘버 사용을 금지했습니다. 화면이 늘어나도 기준이 흔들리지 않게 하기 위해서입니다.

| 항목           | 기준               |
| -------------- | ------------------ |
| 본문 최소 폰트 | 16                 |
| 최소 터치 영역 | 56dp               |
| 주 버튼 높이   | 72dp               |
| 색 대비        | WCAG AA 4.5:1 이상 |

크기 기준만으로는 부족했습니다. 실기기 확인에서 **"눌리는 것처럼 보이는데 눌리지 않는 요소"** 가 반복해서 발견됐습니다. 상세 페이지가 없는 약관 항목에 그려진 화살표(셰브론), 끌 수 없는 시트에 달린 드래그 핸들 같은 것들입니다. 익숙한 사용자는 한 번 눌러 보고 넘어가지만, 익숙하지 않은 사용자는 그 자리에서 "내가 잘못했나" 하고 멈춥니다. 모두 제거했습니다.

### 성과

- **Android 내부 테스트 배포 완료** (릴리스 AAB 서명 빌드 검증)
- 앱·웹 프론트엔드 **1인 전담**으로 Phase 1 전체 기능 구현
- **테스트 42건 통과**, `flutter analyze` error·warning 0건 유지
- `.gitignore`가 `test/` 디렉터리를 통째로 무시해 테스트 대부분이 버전 관리에서 빠져 있던 문제를 발견하고 복구
- 카카오 REST 키를 클라이언트에서 제거(백엔드 프록시 이관), 로그인 실패 시 서버 에러 원문 노출 제거
- 공유 저장에 **멱등키** 도입 — 딥링크를 여러 번 눌러도 여행이 중복 생성되지 않음
- 실기기(Galaxy Note9) 스모크 QA 수행 및 리포트 문서화

## 2. PushOfLife — 응급 구조 지원 · CPR 실시간 피드백

**갤럭시 워치가 낙상을 감지해 자동으로 신고하고, 구조자의 워치에서 CPR 가이드를 자동 실행합니다.**

|        |                                                                 |
| ------ | --------------------------------------------------------------- |
| 기간   | 2024.10 ~ 2024.11 (6주)                                         |
| 플랫폼 | Android App · Wear OS                                           |
| 팀     | 6인 (FE/Mobile 2, WearOS 2, BE 2)                               |
| 역할   | FE/Mobile, UI·UX 디자인, 기획 — **커밋 150개, 팀 내 최다 기여** |
| 성과   | **SSAFY 자율 프로젝트 결선 1위**                                |
| 기술   | Kotlin, Jetpack Compose, Wear OS SDK, BLE, FCM, Twilio          |

### 문제 정의

CPR의 중요성은 널리 알려져 있지만, 실제 상황에서 어떻게 대처해야 할지 몰라 망설이는 사람이 많습니다. 병원 밖 심정지는 초기 몇 분이 생존율을 결정하는데, 그 몇 분이 "신고해야 하나, 내가 해도 되나"를 고민하는 데 쓰입니다. 기존 CPR 앱은 메트로놈 수준의 박자 안내에 그쳐, **지금 제대로 하고 있는지**를 알려 주지 못합니다.

### 담당 업무

- CPR 가이드 화면 — 진입점 3종(연습 / 실전 119 신고 / 환자 워치)별 분기 로직, 가속도 그래프
- 낙상 감지와 자동 신고, Twilio 연동 구조 문자 전송
- BLE 통신 — 모바일·워치 양방향 송수신, 위치 전송
- 위치 권한, AED 지도·길찾기, FCM 알림
- 워치 앱 — 타일(탭 한 번으로 앱 실행), 데이터 수신 및 DataStore 저장, 착용 여부 판별
- 전체 화면 정의서 작성 및 UI·UX 디자인

### 기술적 도전

#### ① 실시간 센서 데이터로 인한 프레임 드랍

**문제** · 가속도 데이터가 초당 수십 회 들어오고, 그때마다 Compose가 재구성되면서 프레임이 떨어졌습니다. CPR 가이드는 **박자를 보여 주는 화면**이라 끊기는 순간 기능의 의미가 사라집니다. 그래프 축이 데이터 범위에 따라 자동으로 조정되는 것도 문제였습니다. 압박 강도가 바뀔 때마다 그래프 전체가 출렁여 오히려 판단을 방해했습니다.

**해결** · `remember`로 가속도 데이터를 캐싱해 불필요한 재구성을 차단하고, `maxData`로 그래프가 보관하는 데이터 개수를 고정해 축이 흔들리지 않게 했습니다. 센서 원시값은 3D 벡터 계산으로 팔 각도를 구한 뒤 저주파 필터와 칼만 필터로 노이즈를 제거했습니다.

**결과** · **프레임 드랍 약 50% 감소.** 압박 리듬이 일정한 폭 안에서 그려져 속도를 직관적으로 인식할 수 있게 됐습니다.

#### ② 오작동이 곧 피해가 되는 기능

**문제** · 자동 신고는 오탐이면 구급차가 헛출동하고, 확신이 설 때까지 기다리면 골든타임을 놓칩니다.

**해결** · 감지 즉시 신고하지 않고, **감지 후 움직임이 있으면 종료하고 없을 때만 신고**하는 2단계 구조로 설계했습니다. 대기 시간도 워치 3초, 모바일 30초로 다르게 두었습니다. 워치는 몸에 착용된 기기라 신호의 신뢰도가 더 높기 때문입니다.

**배운 것** · "감지했으니 알린다"가 아니라 **확신의 정도에 따라 다르게 행동한다**로 설계해야 하는 도메인이었습니다.

#### ③ BLE 3단계 릴레이 통신

환자 워치 → 모바일 → 구조자 워치로 이어지는 통신이라, 한 구간이 끊기면 어디서 끊겼는지 파악하기 어려웠습니다. 특히 **리시버 해제를 빠뜨려 이전 연결이 남아 있는 문제**를 잡는 데 시간을 많이 썼습니다. 연결형 통신에서는 연결하는 코드만큼 정리하는 코드가 중요하다는 것을 배웠습니다.

### 성과

- **프레임 드랍 약 50% 감소** — CPR 가이드 애니메이션 안정화
- 모바일·워치 **BLE 양방향 통신 구현** — 환자 워치를 터치하면 구조자 워치에서 CPR 가이드 자동 실행
- **Android 13(Tiramisu) 대응** — 알림 권한 정책 변경에 맞춰 FCM·포그라운드 서비스 재정비
- 🏆 SSAFY 자율 프로젝트 **결선 1위**

> 상세: cadetbluee.github.io/project/pushoflife

## 3. AllEat — 식단·식비 통합 자동 관리 앱

**결제하면 식단이 자동으로 기록되고, 사진 한 장으로 칼로리까지 인식합니다.**

|        |                                                       |
| ------ | ----------------------------------------------------- |
| 기간   | 2024.08 ~ 2024.10 (7주)                               |
| 플랫폼 | App (React Native)                                    |
| 팀     | 6인 (FE 3, BE 3)                                      |
| 역할   | FrontEnd, UI·UX 디자인, 기획 — 커밋 136개             |
| 기술   | React Native, TypeScript, Redux-Toolkit, YOLOv10 연동 |

### 문제 정의

사전 설문에서 두 가지 불만이 반복해서 나왔습니다. 먹은 것을 일일이 검색해 등록하는 **수기 입력이 번거롭다**는 것, 그리고 **식단 앱과 가계부 앱이 따로 논다**는 것입니다. 건강식을 유지하려면 식비가 오르기 때문에 두 축을 함께 봐야 판단이 서는데, 어느 앱도 같이 보여 주지 않았습니다. 결제 내역을 추적해 기록을 자동화하고, AI 사진 분석으로 수기 입력을 최소화하는 방향을 잡았습니다.

### 담당 업무

프론트엔드 3인 중 **회원, 페이, 식단 기록, 식비, 알림 전 영역**을 담당했습니다.

- 페이 영역 — 페이머니, 결제 내역, 무한 스크롤, QR코드 스캐너
- 식단 기록 — 메뉴 등록·생성 폼, 다이어리 상세, 사진 등록(AI 연동), 즐겨찾기
- 식비 영역 — 집밥·장보기·미기록 식비 등록, 내역 화면
- 레포트 화면 데이터 로딩·렌더링 최적화, 영양 정보 그래프 시각화
- FCM 알림 연동, 기획 단계 설문 설계와 화면 정의서 작성

### 기술적 도전 — 일간 레포트 성능 개선

**문제** · 날짜를 넘길 때마다 같은 데이터를 중복 요청하고 있었고, 하루치 식단이 쌓일수록 칼로리 합산·영양소 비율·지출 집계 같은 파생 연산이 매 렌더링마다 다시 돌았습니다. **열심히 쓰는 사용자일수록 화면이 느려지는** 구조였습니다.

**해결**

- 요청 시점을 정리해 중복 API 호출 제거
- `useMemo`로 파생 연산 메모이제이션
- 결제 내역 조회 범위를 **일주일 단위로 축소**, 검색 결과를 **20개 단위 페이지네이션**으로 전환

**결과** · 렌더링 성능 개선, 네트워크 트래픽 감소, 로딩 상태 정리.

**배운 것** · 최적화 과정에서 의존성 배열을 잘못 잡아 **갱신돼야 할 값이 갱신되지 않는** 버그를 만들었고, 되돌린 뒤 다시 작업했습니다. 성능 개선은 "느린 것을 빠르게"가 아니라 **언제 다시 계산해야 하는지**를 정확히 아는 일이라는 것, 그리고 렌더링을 아무리 최적화해도 애초에 불필요한 데이터를 가져오면 소용없다는 것을 배웠습니다.
