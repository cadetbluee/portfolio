# PushOfLife

> 갤럭시 워치를 활용한 응급 상황 자동 감지 · 신고 및 CPR 실시간 피드백 가이드

## 한 줄 소개

쓰러진 환자를 워치가 자동으로 감지해 119에 신고하고, 주변 헬퍼의 워치에서 CPR 가이드를 자동 실행해 압박 깊이·빈도·각도를 실시간 피드백하는 응급 구조 지원 서비스.

## 문제 정의

- CPR의 중요성은 널리 알려져 있지만, **막상 환자가 쓰러졌을 때 어떻게 대처하는지 모르거나 제대로 못 할까 봐 망설이는 경우**가 많다.
- 병원 밖 심정지(OHCA)는 초기 몇 분이 생존율을 결정하는데, 그 몇 분이 "신고할까 말까 / 내가 해도 되나"로 소모된다.
- 기존 CPR 앱은 메트로놈 수준의 리듬 안내에 그쳐, **내가 지금 제대로 하고 있는지**를 알려주지 못한다.
- → 워치의 기본 센서만으로 (1) 상황을 자동 감지·신고하고 (2) 헬퍼에게 정확한 피드백을 주자.

## 내 역할

**FE / Mobile (모바일 앱 + 워치), UI·UX 디자인, 기획** — 커밋 150개로 **팀 내 최다 기여**

- **CPR 가이드** — 가이드 UI, CPR 시작 기작, 가속도 그래프, 진입점 3종(연습 / 실전 119신고 / 환자 워치) 분기 로직
- **낙상 감지 · 자동 신고** — 낙상 감지 로직, 감지 후 움직임 유무에 따른 신고/종료 분기, 워치 낙상 감지 시 API 전송
- **BLE 통신** — 블루투스 스캔·수신, 모바일 ↔ 워치 양방향 송수신, BLE로 위치 전송, 리시버 해제
- **구조 문자 전송** — Twilio API 연동, 문자 내용 개인화
- **위치 · 지도** — 위치 권한, 서버로 위치·FCM 전송, AED 위치 표시 및 길찾기, 주소 한글 표기
- **알림** — FCM 알림, FCM 메시지 기반 위치 저장, 워치 포그라운드 서비스 중요도 조정
- **워치 앱** — 워치 타일(누르면 앱 실행), 스플래시·아이콘, 워치 데이터 수신 및 DataStore 저장, 워치 착용 여부 판별
- **회원 영역** — 로그인·회원가입 화면 및 디자인, 회원정보 수정(생년월일·성별·자택주소), 응급 환자 정보 저장, 카카오 SDK 초기화
- 전체 화면 정의서 및 UI·UX 디자인

## 핵심 기능

**1. 응급 상황 감지 / 자동 신고**
심박수가 위험 수준 이하로 떨어지거나 낙상이 감지되면 워치에서 사이렌을 울리고, 3초간 반응이 없으면 등록된 응급 연락처와 구급대에 자동 알림. 모바일에서는 30초 무반응 시 자동 신고. 미리 입력된 이름·나이·병력·약물 알레르기를 구급대에 함께 전송한다.

**2. 주변 유저(헬퍼) 알림**
환자 반경 300m 이내 사용자에게 즉시 긴급 알림. 헬퍼는 환자 위치와 주변 AED 위치를 워치·모바일에서 확인할 수 있다.

**3. BLE 기반 CPR 가이드 자동 실행**
헬퍼가 환자의 워치 화면을 누르면 BLE 통신으로 헬퍼의 워치에 CPR 가이드가 자동 실행된다. 워치 타일로 앱에 바로 접근할 수 있어 진입 시간을 없앴다.

**4. CPR 실시간 피드백**
압박 깊이·빈도·팔 각도를 분석해 워치 화면 색상, TTS 음성, 진동으로 전달. 가속도 그래프를 실시간 렌더해 직관적으로 확인할 수 있다. 워치를 착용하지 않은 헬퍼를 위해 환자 워치에서 TTS 안내와 메트로놈을 제공한다.

## 기술적 도전

1. **워치의 기본 센서만으로 CPR 정확도를 판단해야 함**
   전용 하드웨어 없이 가속도계·중력 센서만으로 "압박이 5cm 들어갔는가"를 추정해야 했다. 원시 센서값은 노이즈가 심해 그대로 쓰면 피드백이 요동친다.

2. **실시간 센서 데이터가 UI 성능을 잡아먹음**
   가속도 데이터가 초당 수십 회 들어오는데, 그때마다 Compose가 재구성(recomposition)되면서 프레임 드랍이 발생했다. CPR 가이드는 **리듬을 보여주는 화면**이라, 끊기면 기능 자체가 무의미해진다.

3. **그래프 스케일이 계속 변해 리듬을 읽을 수 없음**
   데이터 범위에 맞춰 그래프 축이 자동 조정되니, 압박 강도가 변할 때마다 그래프 전체가 출렁여 오히려 판단을 방해했다.

4. **3가지 진입점의 상태 분기**
   연습 모드 / 실전(119 신고 동반) / 환자 워치에서의 자동 진입은 각각 신고 여부, 서버 통신, BLE 연결 상태가 다르다. 하나의 화면에서 이걸 다 처리해야 했다.

## 해결 과정

1. **센서 데이터 필터링** — 3D 벡터 계산으로 팔 각도를 산출하고, 저주파 필터와 칼만 필터를 적용해 노이즈를 제거했다. 필터링 후 압박 깊이·빈도 추정이 안정화됐다.

2. **`remember`를 이용한 캐싱으로 재구성 억제** — 가속도 데이터를 `remember`로 캐싱해 불필요한 UI 갱신을 차단했다. 값이 실제로 의미 있게 변할 때만 화면이 다시 그려지도록 했다.

3. **`maxData` 고정으로 그래프 스케일 안정화** — 그래프가 보관하는 데이터 포인트 수를 고정해 축이 흔들리지 않게 했다. 압박 리듬이 일정한 폭 안에서 그려져 사용자가 속도를 직관적으로 인식할 수 있게 됐다.

4. **진입점별 분기 로직 분리** — 3가지 진입점을 상태로 두고 신고 발송·서버 통신·BLE 연결 여부를 각각 다르게 처리하도록 구성했다.

## 회고

> 아래는 **커밋 이력에서 뽑은 초안**입니다. 사실 관계는 커밋에 근거하지만, 판단과 감정은 본인 언어로 다듬으세요.

**1. 오작동이 곧 피해가 되는 기능을 만든다는 것**

자동 신고는 틀리면 구급차가 헛출동한다. 그래서 낙상을 감지한 즉시 신고하지 않고, **감지 후 움직임이 있으면 종료하고 없을 때만 신고하는** 2단계 구조로 바꿨다(`낙상감지 후 움직임 있다면 종료, 없다면 신고`). 워치는 3초, 모바일은 30초로 대기 시간을 다르게 둔 것도 같은 이유다 — 워치는 몸에 붙어 있어 신호가 더 믿을 만하다.
**"감지했으니 알린다"가 아니라 "얼마나 확신하는가에 따라 다르게 행동한다"** — 센서를 다루는 기능에서 가장 크게 배운 지점이다.

**2. 응급 앱일수록 조용해야 한다는 역설**

워치 포그라운드 서비스의 알림 중요도를 낮추는 커밋을 두 번 올렸다(`watch 포그라운드 중요도 낮춤`). 상시 감지를 하려면 포그라운드 서비스가 계속 떠 있어야 하는데, 그게 매번 소리와 진동으로 알림을 띄우면 사용자가 앱을 꺼 버린다. **앱이 꺼지면 응급 감지 기능도 같이 죽는다.**
기능을 살리기 위해 기능의 존재감을 줄여야 하는 상황이었다. 상시 실행 앱은 "잘 동작하는 것"과 "계속 켜 두고 싶은 것"이 다른 문제라는 걸 알게 됐다.

**3. `.gitignore`는 사고가 나고 나서 쓰게 된다**

`gradle.properties`를 여러 차례 커밋했다가 지운 흔적이 남아 있다(`Delete gradle.properties` ×5 → `fix: gradle.properties git 안올리기`). API 키가 들어 있는 파일이었다. 지금이라면 **프로젝트 초기 세팅 단계에서 `.gitignore`부터 잡고 시작한다.** 동행에서 `.env`를 `.gitignore`에 넣고 README에 "절대 커밋하지 마세요, 값은 팀 내부 채널에서 받으세요"라고 명시해 둔 건 이때의 학습이다.

**4. BLE는 "연결됐다"와 "쓸 수 있다" 사이가 멀다**

`bluetooth 수정`, `모바일 블루투스 수정` ×2, `블루투스→워치로 위치전송`, `리시버 해제` — BLE 관련 커밋이 반복해서 올라왔다. 환자 워치 → 모바일 → 헬퍼 워치로 이어지는 3-홉 통신이라, 어느 한 구간이 끊기면 어디서 끊겼는지 알기 어려웠다. 특히 **리시버 해제를 빠뜨려 이전 연결이 남아 있는 문제**를 잡는 데 시간을 많이 썼다.
연결 지향 통신에서는 **연결하는 코드만큼 정리하는 코드가 중요하다**는 걸 여기서 배웠다.

**5. 재발 방지를 손으로 하면 반드시 반복된다**

3일 간격으로 같은 실수를 두 번 했다. 10월 28일에 힙 덤프 파일 3개(`java_pid12616` · `21996` · `23480`)를 지웠고, 10월 31일에 또 3개(`java_pid25392` · `26248` · `3824`)를 지웠다. 빌드 산출물이 저장소에 딸려 올라간 것이다.
바로 사흘 전인 10월 25일, API 키가 든 `gradle.properties`가 올라갔을 때는 파일을 지우는 데서 그치지 않고 **`.gitignore`에 등록**해 다시는 올라오지 않게 막았다(`fix: gradle.properties git 안올리기`). 그런데 힙 덤프는 지우기만 하고 `.gitignore`에 넣지 않았다 — **지금도 `FrontEnd/.gitignore`에 `*.hprof`가 없다.** 그래서 사흘 뒤 똑같이 반복됐다.
**한 번은 실수지만 두 번째는 구조의 문제다.** 같은 주에 한쪽은 규칙으로 막고 다른 쪽은 손으로 치웠는데, 결과가 정확히 그대로 갈렸다. 이후로는 무언가를 지울 때 "왜 이게 여기 들어왔는지"를 먼저 막는 걸 습관으로 삼았다.

### 부록: 힙 덤프 파일에 대한 추정

> 기억에 남아 있지 않은 부분이라, **저장소에서 확인되는 사실**과 **그로부터의 추정**을 나눠 적습니다. 면접에서 물어볼 수 있으니 어디까지가 사실인지 알고 계시는 게 좋습니다.

**확인된 사실**
- 경로는 `FrontEnd/java_pid<PID>.hprof` — `mobile`·`wear` 모듈을 담은 Gradle 프로젝트 루트
- 총 6개, 두 차례로 나뉨 (10/28 새벽 01:39, 10/31 오전 07:19). 각 3개씩 몇 초 간격으로 삭제 — GitHub/GitLab 웹 UI에서 하나씩 지운 형태(`Delete <파일명>`)
- GitHub 임포트 시 `.REMOVED.git-id` 플레이스홀더로 대체됨 → **개별 파일이 100MB를 넘었다**
- `.gitignore`에 `/captures`(안드로이드 스튜디오 프로파일러 저장 위치)는 있으나 `*.hprof`는 없음

**시나리오 A — Gradle 데몬 / Android Studio의 빌드 중 OOM** *(가장 유력)*

`java_pid<PID>.hprof`라는 이름은 JVM이 `-XX:+HeapDumpOnOutOfMemoryError` 옵션으로 **OutOfMemoryError가 났을 때 자동 생성**하는 파일명 형식이다. 작업 디렉터리에 그대로 떨어지므로 Gradle 프로젝트 루트인 `FrontEnd/`에 생긴 것과 정확히 맞는다. PID가 매번 다른 것(3824~26248)도 서로 다른 빌드 프로세스에서 반복 발생했다는 뜻이다.
`mobile` + `wear` 두 모듈에 Jetpack Compose를 쓰는 구성은 Gradle 데몬 힙을 많이 먹어 OOM이 드물지 않다. 그리고 **힙 설정을 넣는 자리가 바로 `gradle.properties`(`org.gradle.jvmargs=-Xmx...`)인데, 10/25에 이 파일이 `.gitignore`로 빠졌다.** 팀원 각자의 로컬 파일이 되면서 힙 설정이 누락됐을 가능성이 있다 — 시점상 그럴듯하지만 이건 추정이다.

**시나리오 B — 앱의 메모리 문제를 직접 프로파일링** *(가능성 낮음)*

실시간 가속도 데이터를 다루는 CPR 가이드에서 메모리 누수를 의심해 힙 덤프를 떴을 수도 있다. 다만 **Android Studio 메모리 프로파일러로 직접 캡처하면 `/captures` 폴더에 다른 이름으로 저장되고, 그 폴더는 이미 `.gitignore`에 있다.** 프로젝트 루트에 `java_pid` 형식으로 남은 건 수동 캡처보다 자동 덤프 쪽에 가깝다.
