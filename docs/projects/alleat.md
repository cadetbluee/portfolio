## 한 줄 소개

'올잇페이'로 결제하면 식단과 식비가 자동으로 기록되고, 사진 한 장으로 칼로리까지 인식하는 핀테크 기반 식단·식비 통합 관리 앱.

## 문제 정의

기존 식단 앱과 가계부 앱을 조사하고 설문을 돌린 결과, 두 가지가 반복해서 나왔다.

- **수기 입력이 너무 번거롭다.** 식단 앱은 먹은 걸 일일이 검색해 등록해야 하고, 그마저도 메뉴명이 정확히 안 나오면 포기하게 된다.
- **식단과 식비가 따로 논다.** 건강식단에 관심이 늘었지만(2024 소비 트렌드: 자기관리 열풍), 건강식을 유지하려면 식비가 올라간다. 두 축을 같이 봐야 판단이 되는데 어느 앱도 함께 보여주지 않는다.

**페르소나**
- 건강한 식단은 챙기지만 식비 관리는 못 하는 사람
- 식비를 줄이다 보니 영양소를 놓치는 사람
- 수기 작성이 번거로워 식단 앱을 이탈한 사람

→ **결제 내역을 추적해 식단·식비 기록을 자동화하고, AI 사진 분석으로 수기 입력을 최소화한다.**

## 내 역할

- **온보딩·회원 영역** — 회원가입 후 초기정보 입력, 초기 유저정보 API 정합, 마이페이지, 회원정보 수정, 체중 변경 모달
- **페이 영역** — 페이머니 화면, 결제내역 컴포넌트, 페이 상세 무한 스크롤, AllEatPay 캐러셀, **QR코드 스캐너**
- **식단 기록 영역** — 식단기록 스크린, 메뉴 등록·생성 폼, 다이어리 상세, 홈 기록 상세보기, 사진으로 등록(AI 연동), 즐겨찾기 토글

## 핵심 기능

**1. 거래 내역 기반 자동 기록**
사용자가 페이머니를 충전해 결제하면, 발생한 거래 내역을 분석해 식비와 식단을 자동 기록한다. 해당 날짜에 결제한 가게의 메뉴를 결제 금액 기준으로 불러와 보여주므로, 사용자는 고르기만 하면 된다. 토글로 여러 끼니를 한 번에 기록할 수 있다.

**2. AI 사진 인식 식단 등록**
YOLOv10 모델로 음식 사진을 분석해 메뉴와 칼로리를 자동 추출한다. 이름을 모르는 메뉴, 검색해도 안 나오는 메뉴도 등록할 수 있다.

**3. 가게 연동 메뉴 DB**
유저가 특정 가게에서 먹은 메뉴를 등록할 수 있게 해, **이용자가 늘수록 다음 사용자의 등록이 쉬워지는** 구조로 설계했다.

**4. 식단·식비 통합 레포트**
일간/주간/월간 레포트를 자동 생성해 섭취 칼로리, 영양소 비율, 지출 내역을 시각화한다. 핵심은 **교차 분석** — 식비는 잘 지켰지만 영양소가 부족한 경우, 반대로 영양소는 충분한데 식비를 초과한 경우를 각각 짚어준다.

## 기술적 도전

**일간 레포트 화면의 데이터 로딩 및 렌더링 개선**

1. **불필요한 API 요청으로 네트워크 부하**
   날짜를 넘길 때마다, 그리고 화면이 갱신될 때마다 같은 데이터를 중복 요청하고 있었다. 레포트는 한 화면에서 식단·식비·영양소를 함께 다루다 보니 요청 수가 빠르게 불어났다.

2. **레포트 데이터가 많을수록 렌더링 속도 저하**
   하루치 식단이 늘어나면 칼로리 합산, 영양소 비율, 지출 집계 같은 파생 연산이 매 렌더마다 다시 돌았다. 데이터가 쌓인 사용자일수록 화면이 느려지는 — 즉 **열심히 쓴 사용자가 손해 보는** 구조였다.

## 해결 과정

- **중복 API 요청 제거** — 요청 시점을 정리하고 이미 받은 데이터를 재사용하도록 바꿔 네트워크 트래픽을 줄였다.
- **`useMemo`를 활용한 연산 최적화** — 칼로리·영양소·지출 집계 같은 파생 값을 의존성이 실제로 바뀔 때만 재계산하도록 메모이제이션했다.
- **데이터 초기화 및 로딩 상태 개선** — 날짜 전환 시 이전 데이터가 잠깐 보이던 문제와 로딩 표시 누락을 정리했다.

## 성과

- ✅ 중복 API 요청 제거 → 네트워크 트래픽 감소
- ✅ `useMemo` 적용 → 레포트 렌더링 성능 개선
- ✅ 데이터 초기화·로딩 상태 개선 → 사용자 경험 향상
- ✅ 결제내역 조회 범위를 **일주일 단위로 축소**, 검색 결과를 **20개 페이지네이션**으로 전환 → 초기 로딩 데이터량 감소
- 프론트엔드 3인 중 **회원·페이·식단기록·식비·알림 전 영역**을 담당 (커밋 136개)
- 설문으로 문제를 검증하고 그대로 기능에 반영한 기획 → 개발 사이클 완주 (7주)

> ⚠️ **채워 넣을 것**: 렌더링 개선 전/후 수치(ms, 프레임)나 API 요청 횟수 감소량. 남아 있지 않다면 위 항목들로도 충분합니다.

## 회고

> 아래는 **커밋 이력에서 뽑은 초안**입니다. 사실 관계는 커밋에 근거하지만, 판단과 감정은 본인 언어로 다듬으세요.

**1. 최적화가 곧 버그가 될 수 있다 — 메모이제이션 오류**

레포트 렌더링을 `useMemo`로 최적화하는 과정에서 메모이제이션 오류를 내고 되돌린 커밋이 남아 있다(`fix: 메모이제이션 오류 해결`). 의존성 배열을 잘못 잡으면 화면은 빨라지지만 **갱신돼야 할 값이 갱신되지 않는다.** 성능 개선은 "느린 걸 빠르게"가 아니라 "언제 다시 계산해야 하는가"를 정확히 아는 일이라는 걸 이때 배웠다. 이후로는 메모이제이션을 넣을 때 의존성이 무엇인지 먼저 말로 설명해 보고 코드를 쓴다.

**2. 화면 간 상태 동기화가 가장 자주 나를 붙잡았다**

`다이어리 생성 후 홈에서 fetch`, `홈으로 돌아갈 때 업데이트`, `다이어리 업데이트 로직 수정` — 같은 문제가 형태만 바꿔 반복해서 올라왔다. 원인은 하나였다. **각 화면이 자기 데이터를 자기가 들고 있어서, 다른 화면에서 바뀐 걸 알 방법이 없었다.** 그때는 화면마다 갱신 시점을 하나씩 심어서 막았지만, 지금 다시 한다면 서버 상태를 화면 로컬 상태와 분리해서 관리했을 것이다. (동행에서 Riverpod로 프로바이더 단위 무효화를 쓰게 된 것도 이 경험이 배경이다.)

**3. 데이터 범위를 좁히는 게 최적화보다 먼저다**

전체 결제내역을 다 불러오다가 **일주일 치로 범위를 좁힌** 커밋, 검색 결과를 **20개씩 끊은** 커밋이 있다. 렌더링을 아무리 최적화해도 애초에 안 가져와도 될 데이터를 가져오면 소용이 없다. "얼마나 빨리 그릴까"보다 "얼마나 안 가져올까"를 먼저 보게 된 계기였다.

**4. 설문으로 시작한 기획의 힘**

설문으로 문제를 검증하고 시작했기 때문에, 개발 중 기능 우선순위를 두고 팀에서 의견이 갈릴 때마다 근거로 돌아갈 자리가 있었다. "수기 입력이 번거롭다(설문 1위)"가 곧 자동 기록 기능의 정당성이었다. 기획에 참여한 프론트엔드로서, **왜 이 기능인지 방어할 수 있다는 것**이 구현 속도만큼 중요하다는 걸 알게 됐다.
